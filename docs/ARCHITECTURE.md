# Architecture

## 1. Shape of the repository

```
jarvis-ai-ios/
├── ios/
│   ├── JarvisCore/Sources/JarvisCore/   Foundation-only engine (tested on Linux)
│   ├── JarvisApp/                       SwiftUI app: App, Design, Features, Screens, Support, Resources
│   ├── JarvisTests/                     Engine test suite (SwiftPM test target)
│   ├── JarvisApp.xcodeproj/             Generated by scripts/generate_xcode_project.py
│   └── Package.swift                    SwiftPM manifest for the engine
├── backend/                             Optional companion service (stdlib-only Python)
├── assets/                              Generated app icon, hero image, previews
├── docs/                                This documentation set
├── agent-memory/                        Engineering memory (constitution, state, decisions, …)
└── scripts/                             Validation, tests, unsigned-IPA build and verification
```

## 2. Why the engine is separate from the UI

`JarvisCore` imports only Foundation. That has three consequences that shaped the
whole design:

1. **It is testable anywhere.** `swift test` runs the 107-test engine suite on
   Linux in about 1.5 seconds, so the logic is exercised on every commit even
   though no CI runner here has Xcode.
2. **The UI stays thin.** Views read state and send intents; no view contains
   business rules. `AppEnvironment` is the single composition root.
3. **Platform work is explicit.** Anything that needs UIKit, EventKit,
   UserNotifications, Speech or AVFoundation is behind a small protocol
   (`ReminderScheduler`, `CalendarBridge`, `SecretStore`) implemented in
   `JarvisApp/Support/`.

## 3. Engine modules

| Module | Responsibility |
|---|---|
| `Core/` | JSON value type, error taxonomy, clock abstraction, logging with redaction, SQLite wrapper, migrations, secret-store protocol |
| `Memory/` | Records and kinds, store with migrations, retrieval scoring, engine rules, conversation store, extractive summariser, memory command parser |
| `Context/` | Prompt assembly under a token budget: system prompt, standing instructions, retrieved memory, summary, active task, recent turns, untrusted blocks |
| `Providers/` | Catalogue of free providers, OpenAI-compatible and Gemini adapters, streaming SSE decoding, retry policy |
| `Networking/` | HTTP transport with timeouts and bounded retries; SSE parser with explicit EOF flush |
| `Tools/` | Tool definition/registration, argument validation and coercion, authorization, execution with timeout, redacted run log |
| `Reminders/` | Natural-language date parsing, recurrence rules, scheduling receipts, reconciliation |
| `Safety/` | Prompt-injection detection and untrusted-content wrapping |
| `Integrations/` | GitHub, Gmail, Instagram, WhatsApp composer, calendar bridge protocol |
| `Agent/` | Assistant state machine, confirmation broker, memory extractor, orchestrator, local intent router |

## 4. A request, end to end

```
user text
   │
   ├─ LocalIntentRouter ──► memory command / time / reminder (no provider call)
   │
   └─ AgentOrchestrator.send
        ├─ MemoryEngine.retrieve           (ranked, untrusted penalised)
        ├─ ContextManager.buildPackage     (token budget, compaction, untrusted blocks)
        ├─ provider.stream(request)        (SSE; cancellable; retries on 429/5xx)
        ├─ tool call proposed?
        │    ├─ ToolExecutor.validate      (unknown args, types, ranges, enums)
        │    ├─ capability + permission gates
        │    ├─ ConfirmationBroker.request (user decision, 300 s timeout → declined)
        │    ├─ execute with timeout; log to tool_runs with redacted arguments
        │    └─ external results wrapped as UNTRUSTED_EXTERNAL_CONTENT
        └─ events: state / memoryContext / textDelta / toolProposed / toolFinished /
                   confirmationRequired / memorySaved / completed / failed
```

The UI consumes the same event stream, so the orb, the transcript, the tool log
and the confirmation card are always describing what is actually happening.

## 5. Memory and context budget

Default `ContextConfig`: 12,000-token budget, 1,500 reserved for the response, at
most 12 recent turns, at most 8 memories, compaction threshold 6,000 tokens. The
window is measured with `TokenEstimator` (characters ÷ 3.5, plus per-message
overhead) because no tokeniser ships with the app.

When the transcript exceeds the budget the manager compacts the **full** transcript
(not a truncated slice) into an extractive summary, stores it as a memory record
with a 30-day TTL, and keeps the recent turns verbatim. Compaction never drops an
active task: the current task line is carried forward explicitly.

## 6. Backend (optional)

`backend/` is a standard-library Python service: HTTP routing, bearer auth with
constant-time comparison, per-caller rate limiting, request size limits, CORS
allow-listing, tool registry and executor, memory store, reminder scheduler with
retry/backoff, OAuth code exchange with PKCE, and an append-only audit log. It
exists for the four things a phone should not do: hold a client secret, hold
privileged integration keys, run scheduled work while the phone sleeps, and keep a
tamper-resistant audit trail.

The app works with no backend. When the backend is absent, the affected tools
report `requiresBackend` and the UI explains what deploying it would add.

## 7. Threading and state

`JarvisCore` uses `@Sendable` value types and a lock-protected SQLite wrapper.
SwiftUI-facing services are `@MainActor`. The orchestrator streams events on a
task; cancelling a turn cancels the provider stream, declines any pending
confirmation and resets the state machine.

## 8. Failure policy

Failures are represented, never swallowed:

* storage failure at launch → recovery screen with the real error, no stub data;
* provider 401/403/429/5xx → distinct errors with distinct recovery advice;
* notification scheduling failure → reminder still saved, `lastError` set, note shown;
* tool failure → recorded in the run log with a redacted error and reported to the
  user and to the model, which is instructed never to claim success;
* retrieval failure → disclosed to the user rather than silently answering from
  an empty context.
