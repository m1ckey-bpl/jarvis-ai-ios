# DECISIONS — jarvis-ai-ios

Format: `D# | date | decision | rationale | alternatives rejected | consequences`
Decisions marked **[OPEN]** await user input. Never delete an entry; supersede it.

---

### D1 — Shared cross-platform Swift engine (`JarvisCore`), thin SwiftUI shell
**Date:** 2026-10-16 · **Status:** ACCEPTED
**Decision:** All logic (memory, context, providers, tools, reminders, integrations, orchestration) lives in a
Foundation-only Swift package `ios/JarvisCore`. The SwiftUI app compiles the *same* source files.
**Rationale:** The development sandbox is Linux with no Xcode → SwiftUI cannot be compiled here, but JarvisCore
**can**, so the majority of app logic is genuinely compile- and unit-tested in this environment; only the thin UI
layer depends on macOS CI. It also keeps the architecture clean and the UI declarative.
**Rejected:** (a) All code inside the app target — untestable here; (b) Kotlin/Flutter/cross-platform — violates R1;
(c) Wait for macOS before writing anything — violates "don't stall".
**Consequences:** PBX project compiles core sources into the app target (no SPM resolution needed); `Package.swift`
exists for SwiftPM/Linux tests; any SwiftUI-only API must stay out of JarvisCore (enforced by `#if canImport(SwiftUI)` guards).

### D2 — Local-first topology; backend is optional, not required
**Date:** 2026-10-16 · **Status:** ACCEPTED
**Decision:** Default runtime = iPhone talks **directly** to a user-configured zero-cost inference endpoint; all
personal data (memory DB, tasks, history) stays on-device. `backend/` is an *optional* companion enabling
server-side secrets, OAuth token exchange, scheduled jobs, and webhooks.
**Rationale:** R10 (zero cost) + privacy + resilience. Free-tier hosting sleeps/sunset; a hard backend dependency
would break the app whenever the host idles. The spec itself demands "keep simple features functional if the AI
backend is temporarily unavailable".
**Rejected:** (a) Mandatory backend — fragile + would require an always-on free host that does not exist reliably;
(b) backend-only memory — contradicts on-device privacy expectations and offline use.
**Consequences:** Every feature must declare `requiresBackend: Bool`; the Settings UI shows a truthful per-feature
status. Backend is fully implemented and independently testable for users who self-host on a free tier.

### D3 — Inference providers: OpenAI-compatible adapter + Google adapter; zero-cost tiers only
**Date:** 2026-10-16 · **Status:** ACCEPTED
**Decision:** Ship a provider abstraction with: (1) a generic **OpenAI-compatible** adapter (covers Groq,
OpenRouter, Cerebras, NVIDIA NIM, Together, local llama.cpp/Ollama/LM Studio, and any self-hosted endpoint) and
(2) a **Google Gemini** adapter. No provider key is embedded; the user pastes their own key into Keychain.
**Rationale:** Maximum portability at zero cost, no vendor lock-in (explicit spec requirement), and it keeps
secrets out of the IPA. Verified free tiers exist for Groq/Google AI Studio/OpenRouter at time of writing
(see `docs/FREE_TIER_POLICY.md` for limits and the caveat that free tiers can change).
**Rejected:** (a) Shipping a bundled API key — breaches R15 and gets revoked; (b) requiring a paid API — R10;
(c) bundling a local model in the IPA — multiple GB, impractical for IPA delivery.
**Consequences:** "Unconfigured" is a first-class UI state with a clear setup flow; the app never fakes inference.

### D4 — PBX project hand-authored, XcodeGen spec provided; core compiled into the app target
**Date:** 2026-10-16 · **Status:** ACCEPTED
**Decision:** `ios/JarvisApp.xcodeproj/project.pbxproj` is written directly (no generator needed to build), and
`ios/project.yml` is provided for XcodeGen users. JarvisCore sources are members of the app target.
**Rationale:** The sandbox has no XcodeGen/Xcode; a directly-buildable project maximizes the chance that CI and the
user's Mac succeed on the first try. Avoids SPM resolution in CI (faster, fewer failure modes).
**Rejected:** SPM-only integration — adds a resolution step and version-sensitivity for zero benefit here.

### D5 — Design: SwiftUI-rendered artwork + one generated raster icon
**Date:** 2026-10-16 · **Status:** ACCEPTED
**Decision:** All backgrounds/motifs/empty-states are drawn natively (Canvas/Shapes/Materials) → tiny bundle,
perfect scaling, dark/light aware, reduced-motion aware. The **app icon** is an original raster generated by an
image model and normalised by a deterministic Pillow script (alpha flattened, sRGB, 1024²).
**Rationale:** Spec asks for lightweight assets and native rendering where more efficient; the icon is the one
place a raster is required by iOS.
**Consequences:** Artwork is reproducible via `scripts/generate_assets.py`; the raw model output is archived in
`assets/app-icon/` with its prompt for provenance.

### D6 — Liquid Glass via availability-gated modifiers
**Date:** 2026-10-16 · **Status:** ACCEPTED
**Decision:** `JarvisGlass` provides `.jarvisGlassSurface()` which uses the system Liquid Glass API
(`glassEffect`) **only** when built with a Liquid-Glass-capable SDK/compiler and running on iOS 26+, and otherwise
falls back to layered `.ultraThinMaterial` + specular stroke; visually equivalent design language on iOS 17/18.
**Rationale:** Spec: "Use Liquid Glass APIs only when supported by the selected SDK and target OS [with] graceful
fallback"; must still compile on Xcode 16.
**Consequences:** Both visual paths must be reviewed; CI compiles the fallback path at minimum.

### D7 — Memory storage engine: SQLite via a thin C-interface wrapper
**Date:** 2026-10-16 · **Status:** ACCEPTED
**Decision:** JarvisCore implements its own small SQLite layer (records, FTS5 + heuristic scoring retrieval,
versioned migrations) instead of SwiftData/CoreData.
**Rationale:** SwiftData/CoreData are unavailable on Linux (kills testability, D1) and heavier; FTS5 gives real
keyword search with BM25 ranking, and structured/typed retrieval is explicitly required by the spec. Semantic
retrieval is layered on top via a pluggable embedder with a deterministic hashing embedder as the zero-cost default.
**Rejected:** (a) SwiftData — untestable here, macOS 14/iOS 17 only; (b) pure JSON files — no FTS, poor scaling;
(c) third-party DB packages — supply-chain + R10 "minimal dependencies".
**Consequences:** Must ship `-lsqlite3` linkage (Apple ships libsqlite3 on iOS) and a Linux modulemap shim.

### D8 — [OPEN] Repository delivery + IPA production path
**Date:** 2026-10-16 · **Status:** OPEN — needs user
**Situation:** This session's GitHub connector is `unsupported`, so the repo cannot be pushed by the agent.
**Options:** (A) user runs `git push` from the prepared local repo; (B) user enables a working GitHub connection so
the agent pushes; (C) user uploads the repo zip manually.
**Also:** IPA must be built on macOS — options: (i) GitHub Actions macOS runner (free for **public** repos);
(ii) user's own Mac; (iii) a free cloud-mac trial.
**Action:** ask the user to choose; no silent assumption is made.

### D9 — Recurrence engine: internal RFC-5545-subset evaluator (no dependency)
**Date:** 2026-10-16 · **Status:** ACCEPTED
**Decision:** Implement `RecurrenceRule` natively (DAILY/WEEKLY/MONTHLY/YEARLY + INTERVAL + BYDAY + COUNT/UNTIL,
time-zone aware, DST-safe), rather than adding SwiftRRule.
**Rationale:** Small, testable, zero dependency, covers the product's stated reminder needs ("every Sunday").
**Consequences:** Unsupported RRULE features are explicitly rejected with a clear error (never silently ignored).

### D10 — Tool authorization model
**Date:** 2026-10-16 · **Status:** ACCEPTED
**Decision:** Tools are declared with `riskClass` (safe/modifying/irreversible/communicating), `confirmationPolicy`
(never/always/onRisk), `timeout`, and required permissions. The **engine** validates arguments and authorizes
execution; the model's tool call is treated purely as a *proposal*. `irreversible` + `communicating` default to
explicit user confirmation unless a narrow, user-configured policy exists.
**Rationale:** Spec §9: "Never trust the model to authorize its own actions."
**Consequences:** Conversation flow must surface confirmation prompts as first-class UI cards.

### D11 — Backend implemented with the Python standard library only
**Date:** 2026-10-16 · **Status:** ACCEPTED
**Decision:** The companion service uses no third-party runtime dependency: `http.server`,
`sqlite3`, `urllib`, `hmac`, `secrets`. `pytest` is the only development dependency,
and `requirements.txt` documents the absence of runtime dependencies explicitly.
**Rationale:** It must deploy on the smallest free tier (or a laptop) with no build step, be
auditable end to end, and let its whole test suite run with no network access. A framework
would add a dependency tree that costs deployment headroom and trust for no functional gain
here (the surface is JSON in / JSON out, ~20 routes).
**Rejected:** (a) FastAPI/uvicorn — needs wheels on the host and a package index at deploy time;
(b) Flask — same objection at smaller scale; (c) the iOS app calling integrations directly — that
would put the OAuth client secret on the device, which R13 forbids.
**Consequences:** Any new backend capability must be implementable with the standard library;
pagination/streaming niceties that a framework provides are deliberately not used.

### D12 — Coding agent scope: plan → branch → commit a document → pull request
**Date:** 2026-10-16 · **Status:** ACCEPTED
**Decision:** The Project & Coding Agent reads a real repository, drafts a plan, then (with an
explicit confirmation) creates a branch named by the user, commits
`docs/jarvis-agent/plan-<timestamp>.md`, and opens a pull request. It never rewrites arbitrary
source files from model output, never merges, never force-pushes and never runs a build it
cannot verify.
**Rationale:** Model-authored source edits committed unreviewed are the single most dangerous
thing an "AI coding agent" can do. A plan document plus a reviewable pull request is genuinely
useful, is fully reversible on GitHub, and never claims a test result it did not observe.
**Rejected:** (a) Let the model emit file contents and commit them — no review gate, high blast
radius, and the app has no way to run or test the result; (b) offer merge/force-push "convenience"
— irreversible without benefit; (c) skip the coding agent entirely — the product spec requires it
as a real capability, not a mock.
**Consequences:** The screen states these limits in-place ("What this agent does not do"), and
every step of a run is reported individually, including partial failure.

### D13 — App composition: single `AppEnvironment` + per-screen views with a view model
**Date:** 2026-10-16 · **Status:** ACCEPTED
**Decision:** One `AppEnvironment` builds every engine, registers tools and capabilities, and is
injected as an `@EnvironmentObject`. Screens are plain views that read capability state and call
engine methods; only the assistant screen has a view model (`AssistantViewModel`) because it owns
a stream. No singletons, no service locator, no third-party state framework.
**Rationale:** It keeps the SwiftUI layer thin (no business rules in views), makes the honest
state of every subsystem observable from one place, and satisfies the "no dead buttons" rule — a
button is disabled because the environment says the capability is not ready, not because a view
tracks its own private flag.
**Rejected:** (a) View models for every screen — ceremony with no testability benefit here (none of
them can be compiled in this environment anyway); (b) global singletons — untestable and hides
dependency order; (c) TCA/Redux — an unnecessary dependency for an app of this size.
**Consequences:** The environment's initialiser performs every dependency in order and surfaces a
real error (never stub data) if storage cannot be opened; the recovery screen consumes that error.

### D14 — Backend secrets at rest: documented keystream encryption, not "military-grade"
**Date:** 2026-10-16 · **Status:** ACCEPTED
**Decision:** Stored OAuth refresh tokens are encrypted with an HMAC-SHA256 keystream keyed by
`JARVIS_BACKEND_TOKEN`, with an integrity tag, and the code and docs state plainly that this is
defence-in-depth against a leaked database file — not a substitute for platform disk encryption.
**Rationale:** The alternative without a cryptography dependency is either storing plaintext or
pretending. Pretending is forbidden by the constitution; plaintext is worse. Being explicit about
the guarantee's limits is what makes the choice honest.
**Rejected:** (a) Add `cryptography`/`pycryptodome` — a heavy dependency for a value that the
operator's disk encryption already covers; (b) store plaintext with a warning — a leaked backup
would expose live Gmail access.
**Consequences:** Operators are told, in `docs/SECURITY.md` §8 and `backend/README.md`, to enable
platform disk encryption and to keep the token out of logs.

### D15 — Verification strategy without macOS: parse + structure + synthetic artefacts
**Date:** 2026-10-16 · **Status:** ACCEPTED
**Decision:** Since no macOS exists here, verifiability is constructed deliberately:
`swiftc -parse` over every Swift file, structural validation of the generated
`project.pbxproj` (object counts, dangling references, delimiter balance, source
coverage), a repository validator that asserts layout *and* policy, and an IPA verifier
exercised in both directions with synthetic well-formed and malformed archives.
**Rationale:** The constitution forbids claiming unverified results. Rather than write "should
build", the project states exactly which claims carry evidence and which do not
(`docs/DEFINITION_OF_DONE.md` §5), and turns every remaining claim into a named command.
**Rejected:** (a) Report the app as "built" from parse checks — a lie; (b) say nothing — hides the
largest risk in the project.
**Consequences:** CI runs the same validators, so the checks cannot rot; the DoD document must be
updated whenever a *not verified* row becomes verified, with the observed output.

### D16 — Secret-scan exclusions require an in-file marker
**Date:** 2026-10-16 · **Status:** ACCEPTED
**Decision:** `.secretsignore` may exclude a file from the credential-shaped-string scan only if
the file itself contains the marker `synthetic-credential-fixture`, and the validator fails the
build otherwise.
**Rationale:** A plain exclusion list is exactly how a real leak would be hidden. Requiring the
marker in the file means an exclusion cannot be added silently for a file that actually contains
a live key without a reviewer seeing the claim in the diff.
**Consequences:** Four test files carrying deliberately fake key shapes are excluded; all four
carry the marker; the validator prints each exclusion it honours.

### D17 — The real toolchain is the only judge of "it compiles"; keep the red runs
**Date:** 2026-10-16 · **Status:** ACCEPTED
**Decision:** Compilability claims come from an actual macOS build. Four CI runs were
allowed to fail on real defects, and every failure is kept in `docs/TEST_REPORT.md` §6
rather than deleted or re-run into silence.
**Rationale:** `swiftc -parse` on Linux, balanced-brace checks and even the author's own
plist parser cannot see a toolchain-specific concurrency diagnostic, an unquoted comma in
a project file, or a missing `import UIKit`. Each of those was found only by running the
real thing — which is what the DoD rule ("name the command that produced the claim")
exists to force.
**Consequences:** Any future claim about the app must cite a workflow run, not a parse
check; the four red runs stay part of the project's history.

### D18 — A tagged release is the durable delivery channel for the IPA
**Date:** 2026-10-16 · **Status:** ACCEPTED
**Decision:** A `v*` tag makes CI rebuild the IPA and attach it (with its SHA-256) to a
GitHub Release, in addition to the 90-day workflow artifact.
**Rationale:** Artifacts expire. The user needs a link that still works when they get
round to signing, and a checksum they can verify independently.
**Consequences:** Releases contain an *unsigned* build; the release notes say so, and the
signing step remains entirely the user's.
